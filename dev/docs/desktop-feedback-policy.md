# Desktop 反馈与诊断的信息层级

Desktop 主区应帮助用户理解当前动作的结果，以及可以立即采取的下一步。诊断是辅助观察，不是运行、审批、保存或恢复操作的额外许可。本策略落实[代码规范 §1.4](../governance/code-standards.md#14-辅助观察不得阻断用户操作)，不更改后端 authority 或持久化真相。

## 主区反馈

只有明确影响当前操作的事实，且产品提供真实可用的下一步，才使用醒目的警告或错误反馈。例如本页诊断请求失败提供重试；刷新失败说明仍在显示上次结果；报告保存失败提示重新选择位置。已有审批拒绝、权限边界、资源准入、CAS/写入冲突和真实请求失败继续在各自操作边界表达，不能因界面简化而消失。

辅助观察未知、未验证、过期或不可用，不得自动解释为当前工作无法继续，也不能改写成健康或成功。没有可执行下一步时，放入中性技术详情，保持用户可以查阅原始事实。分享前检查报告属于中性说明，不默认使用黄色警告块。

## 结构化分类与能力边界

展示与动作必须来自稳定的结构化标识、明确状态和受支持的操作契约。禁止用英文或中文关键词、正则、自然语言建议、相同文案推断根因或功能行为；同根因合并也必须有可信的 typed identity。没有这个身份时，原样保留不同记录，不能因为文案相似而去重。

当前 `SupportDoctorReport.checks` 仅提供 `status/name/summary/remediation`，没有诊断 ID、当前操作影响范围或允许的修复动作。`name` 是技术标签，不是 renderer 可以自行扩展的修复路由。因此支持页保守地将这些记录全部按原顺序放入默认折叠的“技术详情”，保留每条状态、说明和建议，不生成“修复连接”“调整外观”等未经契约确认的动作。

`cutover` 的 blocker code/adapter 是结构化观察身份，但它本身不能证明当前已附着会话的运行状态。支持页保留原始 epoch、authority 和 blocker，不将观察投影不完整包装成用户必须解决的运行阻断。支持页不从总体 `ok/warn/error` 汇总得出“运行正常”或“当前任务失败”的结论。

后续只有公共契约提供了当前影响、精确对象身份和真实允许的恢复动作，才可以把对应条目提升到主区。单纯增加关键词映射或跳转设置页不能补足这些证据。

## 支持页呈现与报告保真

- 主区显示“诊断报告”、生成时间、重新检查、问题入口及保存报告，避免把诊断汇总包装为整机健康结论。
- 技术详情保留原始总体状态、计数、全部检查及 cutover 信息；不改变 status，不按相同文字合并检查，也不丢弃未知记录。
- 重新检查时保留当前报告；刷新失败保留原生成时间并明确旧结果，不能把旧报告标为本次成功。跨工作区晚到响应不得替换当前报告。
- 报告隐私类别及已脱敏边界保持，导出仍由原生业务 command 完成；renderer 不取得报告内容、目标路径或 bearer。
- 控制日志恢复继续使用原有独立预览、确认和 typed 错误，不从普通诊断记录自动触发。

## 会话列表与插件观察

历史列表的 degraded、identity conflict、扫描排除计数按各自字段保留在中性详情中，不相加为“问题总数”，也不据此限制可用会话。具体来源的 `sourceState` 仍决定能否打开及支持哪些管理动作；真实列表请求失败继续提供刷新入口。

插件 catalog 仅提供 warningCount，没有逐项诊断身份或修复动作。计数保留在默认折叠的中性技术详情，不能凭计数推断某个插件可以被信任或需要清理。实际加载、决定保存和进程清理失败继续保留原错误及重试；权限与审批行为不变。

报告隐私的长列表、范围说明及类别标识默认收进“报告内容”，分享前检查已保存 JSON 的重点提醒保持可见。主区不重复说明下方还有详情。

## 验证边界

组件回归覆盖：仅有未知或不可操作记录时不出现主区红黄告警或健康结论；原始 error/warn/ok 与重复文案的独立记录保留；展开技术详情；刷新期间保留报告、刷新失败、初读失败重试、跨工作区晚到响应、双语隐私展示、导出失败和取消。真实 Desktop 的折叠、窄窗口、键盘焦点及诊断重跑需要另由 cua-driver 复验，组件通过不替代原生证据。
