# Desktop / TUI 真实需求体验与验收基线

调研日期：2026-10-20；仓库落地：2026-10-21。本文定义双端真实需求体验的问题分类、通过条件和记录方法；
它是验收基线，不表示当前版本已通过。具体覆盖和缺陷状态由每轮体验报告提供证据。

## 1. 目标与适用范围

用户能够在 Desktop 和终端交互端完成真实任务，看懂进展和结果，控制执行过程，
并在出错后继续工作。功能正确性与 UI/UX 同时验收：两端都必须简洁明了、突出重点，
不在默认界面堆积对当前用户决策无用的信息。

Desktop 与 TUI 是并列的一等产品表面，共享 kernel/runtime 的任务、审批、恢复与验证语义。
日常口语中的“CLI 体验”如果指终端里的交互界面，报告应标为 TUI；自动化 CLI 的
输出、退出码和非交互行为另行检查，不用命令数量衡量产品能力。

本轮主任务的目标补充如下，可直接引用到 goal 或执行计划：

> 以真实需求依次体验终端 TUI 和 Desktop；两端的用户操作均通过 cua-driver
> 驱动真实原生窗口完成，使用等价且独立的初始项目。按本文验收任务结果、输入、
> 状态真实性、审批、停止与恢复、稳定性、信息层级、文案、布局、可访问性及数据边界。
> 每项结论保留版本、步骤、用户影响和证据；分别记录功能问题与 UI/UX 问题，
> 区分产品、模型、环境及驱动原因。默认界面只突出目标、状态、结果、下一步和必要风险。
> 使用独立业务检查核验产物；结构化测试不能代替真实界面体验。
> 分别报告两端通过、失败、阻塞和未覆盖的范围，不以单端成功、模型宣称完成或绕过操作
> 关闭验收。本文是体验与验收要求，不自动将本轮发现的问题标为已修复。

## 2. 研究依据与使用边界

- [NN/g：10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)
  支持状态可见、用户控制、一致性、错误恢复及精简信息。精简要求保留与任务有关的信息，
  而不是隐藏失败、风险或不确定性。
- [Microsoft Research：Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/)
  支持表达能力与局限、展示当前相关信息，以及方便用户取消、纠正和控制 AI 的行为。
- [Command Line Interface Guidelines](https://clig.dev/) 提供人类可读输出、
  错误处理、退出码、标准输出与诊断输出分离等约定。该指南明确不覆盖完整全屏 TUI，
  因而不能代替终端交互验收。
- Desktop 使用 WCAG 2.2 的
  [键盘操作](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)、
  [焦点可见](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible)、
  [焦点不被完全遮挡](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum)、
  [状态消息](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)和
  [文本对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
  作为可访问性检查依据。完整 WCAG 合规需要逐项验证，不能由一次截图或 AX 快照推导。

上述来源于调研日期查阅。下文的场景、记录格式、严重程度和时间目标是 Sigil 的验收约定，
不宣称为这些来源规定的统一行业门槛。

## 3. 两端共同验收矩阵

| 编号 | 问题类型 | 需要记录的表现 | 通过条件 |
| --- | --- | --- | --- |
| A01 | 任务结果与正确性 | 漏需求、错误产物、只解释不执行、未经验证就宣称完成 | 对照事先定义的业务结果独立核验；实际产物、验证结果和最终说明一致；明确未完成部分 |
| A02 | 入口与引导 | 隐藏的信任确认、空白页、无法发现下一步、无解释的禁用 | 当前项目和输入入口可识别；真实前置条件可见并有解决动作；辅助诊断缺失不额外阻止已授权工作 |
| A03 | 输入与意图承接 | 丢字、重复发送、中文合成误提交、追加要求丢失或进入错误会话 | 输入完整保留；发送、排队、修改、取消结果明确；运行中追加输入何时生效可理解 |
| A04 | 状态真实性 | 已取消仍显示进行中、计数陈旧、费用未知显示零、假进度 | 标题、状态、操作和历史一致；区分运行、等待确认、停止中、终态与失败；未知如实显示 |
| A05 | 审批与权限 | 预览丢失、风险标签矛盾、影响范围不清、碎片化确认、拒绝后仍执行 | 用户可检查动作、目标、影响、风险和授权范围；等待或重连不丢失对应请求的预览；实际执行符合预览和授权；拒绝有效 |
| A06 | 暂停、停止与恢复 | 无法停止、停止后仍发生新业务修改、历史丢失、重复执行 | 请求停止与实际停止区分；已有副作用如实保留；未确认清理不能声称全部停止；恢复不静默重复副作用，两端同名动作语义一致 |
| A07 | 错误与稳定性 | 崩溃、无限等待、断网后卡住、切换模式后异常 | 常见失败有明确原因与可行下一步；已输入内容和已完成工作保留；重试不重复修改；普通操作不崩溃 |
| A08 | 信息层级与简洁性 | 内部字段外露、重复状态、长日志淹没结果、统计挤占空间 | 默认内容服务当前任务；结果和待处理事项突出；详细日志、参数与统计按需展开 |
| A09 | 文案与一致性 | 中英文混杂、内部术语、同词异义、按钮与行为不符 | 使用可理解的用户语言；产品文案本地化；代码、标识符等按原义保留；动作名称与后果一致 |
| A10 | 布局、可访问性与响应 | 截断、重叠、焦点丢失、仅靠颜色、输入与滚动卡顿 | 支持范围内的尺寸和缩放可用；主要内容与操作始终可达；焦点清楚、键盘可操作、操作有及时反馈 |
| A11 | 数据与工作区边界 | 改错项目、覆盖无关修改、凭证外露、恢复越界 | 修改限于授权范围；保留无关工作；凭证不进入普通输出；项目切换与恢复保持正确归属 |

同一问题可以命中多个类别。归因尚不明确时保留用户可见事实，不凭文案猜测内核状态，
也不因模型参与执行而把所有问题归为模型问题。

## 4. 简洁明了的具体标准

默认界面应帮助用户回答四个问题：**正在做什么？现在是什么状态？结果是什么？
需要我做什么？** 必要风险、限制和不确定性同时保留。

- 等待审批时突出待批准的动作、影响及选择；完成时突出结果、产物入口和验证情况。
- 同一状态不在标题、卡片、输入框反复强调；长任务描述不在侧栏和页头完整重复。
- 普通工具成功优先给简短摘要；完整命令、文件差异、输出可以查看。
  内部 ID、状态枚举、资源参数和诊断字段不占据默认主流程。
- 审批精简不能隐藏影响决策的信息。相关变更可以合并审阅，但不能因此扩大授权范围。
  无法判断影响时，用明确语言说明不确定性和需要检查的内容。
- 错误说明发生了什么、影响哪些结果、用户如何继续；堆栈和协议字段放到诊断详情。
- 费用无法估算时显示未知，不能显示零；Token、缓存等统计按需查看，
  只有已影响预算或任务执行时才进入主要状态提示。
- 结束过渡状态后清除失效提示；历史审批显示已处理结果，不继续伪装成待用户决定。
- 对每项默认可见信息说明它支持哪项用户决策；不能说明的内容应删除、合并或移入详情。
- 记录真实困惑、额外操作和错误选择，避免仅用“看起来不好看”作为 UX 缺陷依据。

例如，未知费用显示 `0.0000` 对应 A04，已取消的卡片仍写“正在进行”对应 A04/A09，
审批界面被内部字段占满对应 A05/A08。这里是分类示例，不代替具体版本的复现证据。

## 5. 各表面专项检查

### 5.1 终端 TUI

- 中文输入、emoji、多行粘贴、光标移动和历史输入正常；发送与换行规则明确，
  输入法合成过程中不提前发送。
- 快捷键提示与行为一致；确认、拒绝、关闭弹层、退出有可发现入口；
  不吞掉用户输入而不解释原因，弹层退出后焦点合理恢复。
- 在记录的终端类型、字体、行列尺寸下检查长路径、代码、差异和表格；
  缩窄、缩短及连续调整尺寸后无内容重叠、残影或操作位置错配。
- 跟随最新内容与阅读历史明确分离；新输出不强制打断正在阅读的历史位置。
- 正常退出及异常恢复后，终端回显、光标和输入模式正常。
- 记录终端和辅助技术的实际支持范围；不能由 Desktop 可访问性通过推导 TUI 通过。

### 5.2 Desktop

- 设置分为连接与模型、外观与偏好、扩展、支持四组；分类切换保留未保存草稿，
  向导进入及切换步骤时首个控件可见，取消后回到原触发控件。
- 会话库默认突出搜索与记录，批量工具在选择记录后显示；全选入口仍可发现，
  批量修改继续经过原有精确预览、阻断项展示与明确确认。
- 支持页优先呈现失败、警告和建议动作，通过的检查按需展开；未知、权限、资源与隐私事实仍可查看。
  命令记录恢复错误仅表达已知原因；预览失效后，即使重新预览失败，也必须保持禁止确认，
  直到取得新预览；工作区或会话切换不得沿用旧预览。
- 扩展区分别表达没有来源、没有筛选结果及不可用状态；仅对已知枚举使用产品文案，
  未知值与真实原因保持可查。恢复抽屉中当前文件检查点排在分支与结论之前；选择 Agent 只建立输入绑定。
- 工作区、会话和任务层级清楚；切换、关闭、重开后的状态与事先提示一致；
  草稿、滚动位置及待处理审批不会无解释丢失。
- 长会话、侧栏、弹窗及窗口缩放不遮挡主要操作；弹层关闭后焦点合理恢复。
  尺寸与原生 smoke 范围复用 [Desktop dogfood 指南](desktop-dogfood.md)。
  原生紧凑窗口预算为 840×560 逻辑点，宽度小于 900px 时使用会话导航抽屉；
  检查输入、预览及当前审批同时存在时仍能读取正文和作出决定，并验证重开恢复该尺寸。
- 核心流程可以用键盘完成；焦点可见且不被完全遮挡；无意外键盘陷阱，
  模态界面的焦点约束与退出行为清楚。
- 抽屉或对话框中的筛选、菜单等浮层归属当前模态，避免被遮罩覆盖或滚动区裁切；
  背景及后加入的背景节点保持隔离。Escape 先关闭当前浮层并回到触发控件，
  再次按下才关闭所属模态；子对话框活动期间，旧浮层不得截获按键或抢回焦点。
- 控件具有可访问名称；重要状态变化可由辅助技术识别，而无需反复抢焦点。
  原生窗口及屏幕阅读器检查与 DOM/AX 结构检查分别保留结果。
- 错误不只依赖颜色。按 WCAG 1.4.3 检查普通文本至少 4.5:1、
  大文本至少 3:1，并按该条款定义及例外判定，不把该比例套用于所有控件。

### 5.3 两端语义对齐与自动化 CLI

相同业务场景共享任务规则、权限范围及恢复含义；界面布局可以不同。
如果“停止”“暂停”“取消”后是否可继续不同，必须在操作前表达后果，
不能要求用户先理解内部 run/task 分层。

自动化 CLI 补查成功和失败退出码、结果与诊断输出分离、机器可读格式稳定、
非交互环境不等待无法完成的输入、不输出动画，以及简短帮助和可行动错误。
这些检查不能替代 TUI 的真实交互体验。

## 6. 场景、环境与证据

### 6.1 六组场景

| 场景 | 主要过程 | 主要验收点 |
| --- | --- | --- |
| 首次进入 | 启动、选项目、必要配置与信任确认、首条请求 | 入口、引导、键位与前置条件 |
| 只读理解 | 阅读现有项目，回答具体问题 | 答案依据正确，项目文件保持不变 |
| 完成修改 | 实现需求、预览、审批、执行验证、交付 | 审批与实际效果一致，独立业务检查通过 |
| 中途调整 | 追加要求、拒绝一次操作、纠正错误 | 输入承接、拒绝有效、纠正成本可接受 |
| 中断恢复 | 执行中停止、退出重开、恢复和继续 | 真实停止与历史一致，不重复副作用 |
| 异常与压力 | 网络或工具失败、长输出、小窗口、会话切换 | 状态清楚、界面可用、错误可恢复 |

可以把多组场景组合为一个真实项目的多个回合；必须逐项标记覆盖，
不能在任务已完成后点击停止，却宣称验证了执行中停止。

### 6.2 操作与隔离

- 本轮终端与 Desktop 均通过 cua-driver 操作真实应用窗口；
  终端通过原生 Terminal 输入和观察。不把后台直接发命令当作用户交互证据。
- 为两端准备等价且独立的初始项目、会话及配置状态；不把第一端的实现或答案带入第二端。
  保留初始文件摘要及必要的独立 Git baseline，防止借用父级产品仓库状态。
- 记录版本、源码标识、binary/app 身份、平台、provider/model、权限模式及窗口尺寸。
  记录配置标签和差异，不导出凭证。
- 环境准备、只读诊断和独立产物核验可用专用检查；清楚区分其结果与真实 UI 操作证据。
  测试隔离遵守 [test-isolation.md](test-isolation.md)，不继承真实用户状态，
  不用共享 state/cache 覆盖 fixture 的显式存储。
- 业务 oracle 和额外验证数据保留在观察员一侧。模型自己的测试通过，
  不能替代对金额、文件内容等业务结果的独立核验。
- 每轮报告留在 ignored 本地体验目录，例如 `.repo-local-dev/dogfood/<campaign>/`。
  版本化文档保留规则与经过审阅的摘要；原始会话、截图、日志及工作区内容不自动提交。

### 6.3 证据与时间目标

结构化测试证明状态、协议或持久化事实；真实界面观察证明用户能看见并操作它们；
独立产物检查证明业务结果。三者分别记录，不能互相替代。

首轮采用以下项目时间目标，记录测量方法后再按数据校准：

- 关键点击和按键从产品接收到输入起，1 秒内有可见反馈；模型生成完成时间另计。
- 持续等待时有真实阶段或等待原因及可用控制入口；无法估算时不显示伪造百分比。
- 停止请求得到反馈与实际清理完成分别计时；响应目标不能作为强写成功终态的依据。
- 若 cua-driver 的调度、窗口激活或截图间隔影响测量，记录观测上界或标为未测，
  不把驱动延迟归为产品延迟。

同时记录任务完成率、用户决定次数、重复输入次数、找不到入口的步骤、
需要开发者解释的节点和实际耗时。首次使用者应能依靠产品本身完成核心流程；
代理熟悉源码后自行猜中的隐藏操作不能作为入口清楚的证据。

## 7. 问题记录、分级与关闭

### 7.1 记录模板

```text
编号：
表面、版本与环境：
场景、用户目标与前置条件：
最短复现步骤：
预期表现：
实际表现：
用户影响：
分类（A01–A11，可多选）与严重程度：
归因（产品 / 模型 / 环境 / 驱动 / 待查）：
证据状态（已确认 / 待验证）：
复现次数 / 尝试次数：
证据（截图、录像、事件、日志、产物核验）：
改进建议：
修复后通过条件：
复验版本、步骤、结果与剩余限制：
```

功能问题和 UI/UX 问题使用同一记录要求。先保留事实和影响，
不以技术根因尚未定位为由丢弃体验问题；定位后再更新归因。

### 7.2 严重程度

| 等级 | 判断标准 |
| --- | --- |
| P0 | 数据破坏、凭证泄漏、严重权限绕过 |
| P1 | 核心任务无法继续、崩溃、无法停止，或误导用户作出高风险决定 |
| P2 | 能完成，但持续造成困惑、重复劳动、错误选择或明显操作负担 |
| P3 | 局部文案、间距或视觉一致性问题，基本不影响理解和操作 |

按影响而非所属模块分级：审批内容不可见等 UI 问题也可能是 P1。
驱动未把键送入目标窗口不是已确认产品不响应；短暂恢复提示不是死锁证据。

### 7.3 场景结论与通过条件

场景分别记录 `passed`、`failed`、`blocked`、`not_covered`；
未结束的执行可以暂记 `in_progress`。已通过的部分写清范围。
已确认产品故障导致后续无法执行时，故障本身记录失败，后续场景记录阻塞，
不把阻塞、未执行或依赖绕过完成的主路径记为通过。

本轮完整验收通过要求：

1. 两端核心场景分别通过，业务产物经独立检查符合要求。
2. P0/P1 清零；影响状态理解、审批决策或结果可信度的 P2 修复并复验。
   其余 P2 明确处置、影响和是否接受，不能静默忽略。
3. 核心路径无输入丢失、重复执行、错误完成声明和未经授权的修改。
4. 修复按影响运行相关隔离测试，并回到原表面复验对应场景；
   不因源码检查或单元测试通过直接关闭真实体验缺陷。
5. 报告明确平台、配置、版本和未覆盖范围；不把一端或一个平台的成功扩为全产品通过。

“体验调查已完成”与“产品验收已通过”分别报告：调查可以交付完整问题清单，
即使其中仍有失败或阻塞；不能因此把产品标为验收通过。
